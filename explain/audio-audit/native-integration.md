# Native audio audit

> Parent root results: the [consolidated audit](../audio-engine-audit.md) takes precedence for aggregate validation counts and later root findings. This specialist note records the native source, platform, artifact and signing evidence; it does not replace the root's release-readiness verdict.

This note records the native portion of the repository audio audit. Build results below are updated after execution. Native compilation and JavaScript event simulations do not establish physical lock-screen, Bluetooth, call, or manufacturer battery-policy behavior.

## Installed versions and runtime ownership

- Installed Expo Audio is 57.0.5; its Android Gradle file declares Media3 1.9.0, and release dependency resolution confirms ExoPlayer 1.9.0. React Native is 0.86.3, Expo is 57.0.27, and React Native Audio API is 0.13.6. These are the current installation, rather than the historical SDK 54 / React Native 0.81 architecture in the request.
- Custom Android/iOS builds use `StandardAudioPlayer.tsx` and React Native Audio API. Its single shared `AudioContext` owns decoded audio and the equalizer graph. Android notifications and OS commands use Audio API's `MediaSessionCompat`, shared with the Android Auto browser. Android Auto is a catalog/control bridge, not another player.
- Expo Go uses the separate Expo Audio adapter because Audio API's custom native bindings are unavailable in that runtime. Expo Go uses its own compiled native package and manifest: repository native patches do not update the installed Expo Go binary. Expo Audio has seek/skip-interval controls, but not the app's custom Android Auto queue controls.
- Generated Android `AudioControlsService` is disabled. The app's Audio API `CentralizedForegroundService` is the playback foreground-service owner. The prebuild plugin now preserves that distinction instead of losing the disabling during regeneration.
- Android Auto retains one process-wide shared media-session token so an activity/React context change does not invalidate a connected car's token. Notifications, focus, and registered receivers belong to the current Audio API bridge and are cleaned at bridge invalidation. Notification callback dispatch resolves the current bridge, rather than the bridge captured when the session was created. This does not implement cold process restart/resumption from the car; without a running app bridge, the car service reports that the app must be opened.

## Confirmed defects and remediation

1. **High — Android headset removal was never delivered to the JS route handler.** The installed Android package had the `ROUTE_CHANGE` enum, but no receiver for `ACTION_AUDIO_BECOMING_NOISY`. Added exactly one receiver that publishes the existing `reason: OldDeviceUnavailable` event; the app's existing route handler pauses instead of unexpectedly routing to the speaker. Wired/A2DP physical behavior remains untested.
2. **High — denied Android focus did not change application playback intent.** The native package ignored failed focus requests; the void bridge API cannot report a result directly. It now emits the existing interruption-began event with `shouldResume: false` when focus is denied. Root changes record intent before requesting focus so this event cancels the attempt. A separate focus controller was not introduced. Android 15+ requires top-app or foreground-service eligibility. The void focus bridge and denial event are asynchronous: the JS regression proves cancellation when the interruption is delivered, but does not guarantee prevention of a brief start before delivery. Foreground-service readiness is not guaranteed by the notification promise: native `showNotification` resolves after sending the service start intent, before the OS executes `onStartCommand`/`startForeground`. Selected/paused playback normally already owns a service; restarting after terminal state or from a background/car action may still receive a focus denial. Cold/background restart eligibility and timing remain unverified; no new native acknowledgement/timeout contract was added without device evidence.
3. **Medium — native bridge invalidation leaked OS receiver/focus/notification ownership.** Upstream Android invalidation only cleaned the foreground service. Added owned cleanup for notification registry, focus, noisy/media receivers, and observed volume receiver; repeated initialization cleans the previous installation first. An older bridge cannot clear a newer bridge's installation. Added idempotence to volume observation.
4. **High — persistent shared media-session callbacks captured an outgoing React bridge.** Notification callbacks now dispatch through the current `PlaybackNotificationReceiver` bridge reference, preserving the car token through React context recreation while avoiding stale JNI event dispatch. True process recreation remains a separate unsupported resumption path.
5. **Medium — hiding playback left native metadata and playback controls attached to the shared session.** Hide now clears metadata and publishes `STATE_NONE` with only the supported catalog-start commands, preserving the token needed by the browser. Root handles genuine stop/queue-exhaustion notification termination in JS.
6. **High — iOS artwork completion could overwrite a newer track or recreate metadata after hide.** Replaced unowned synchronous remote artwork loads with one cancellable `NSURLSessionDataTask`, a 10-second request timeout, an artwork generation, and an active-notification check. A changed/missing artwork URL immediately clears the old art; same-URL updates do not start concurrent requests. Local file decoding remains off the main queue and completion is guarded.
7. **Medium — iOS notification operations and cleanup raced across global worker queues.** Show/hide/isActive operations now run serially on the main queue with their matching notification cleanup. System notification cleanup removes all observers and stops any optional secondary-audio timer before releasing the manager.
8. **Medium — Expo Audio iOS closure targets accumulated.** `MPRemoteCommand.addTarget(handler:)` returns an opaque target. The installed source re-added closure handlers and attempted to remove `self`, which did not own those handlers. The patch retains the returned command/token pairs and removes only those tokens before re-registering or clearing controls. Stock Expo Go cannot receive this source patch without an upstream/new binary update.
9. **Medium — car queue IDs could overflow Long-to-Int conversion and the published active queue item lagged catalog updates.** The Kotlin bridge now validates bounds before conversion and refreshes playback actions after queue/active-item updates. Generated and plugin Kotlin sources stay identical.
10. **Low — prebuild drift and unused native state/hooks.** The Android Auto plugin now retains the generated disabling of Expo Audio's service. Removed two patched static session/metadata listener hooks with no external registration or callers, the now-unused captured Audio API constructor/import, and the ineffective macOS-only `MPNowPlayingInfoCenter.playbackState` branch from iOS code. iOS progress continues to use `MPNowPlayingInfoPropertyPlaybackRate` and elapsed time. No TrackPlayer engine dependency is installed; root removed the old `com.doublesymmetry` Proguard keep rule from the source configuration and generated rules, and a final search confirms its absence.

## Native command mapping

| OS/native command | Native payload | Existing application owner |
| --- | --- | --- |
| Play, pause, stop | Audio API playback-notification event, no position | Standard adapter dispatches the matching remote event/action; no direct second native player control. |
| Next / previous track | Distinct `NEXT_TRACK` / `PREVIOUS_TRACK` events | Queue selection, rather than seeking within the selected track. |
| Seek to position | Android media-session milliseconds divided by 1000; iOS `positionTime` already seconds | Existing `RemoteSeek` handler receives seconds, preserving track identity. |
| Fast forward / rewind interval | Android skip interval 15 seconds; iOS command `event.interval` | These are separate skip-interval events. The custom app disables the interval controls and enables next/previous track controls. |
| Car play media ID / search | Shared session callback → native library module → JS car event | Existing resolver/queue controller selects the catalog item; unavailable JS bridge reports open-phone error. |
| Car skip queue item | Validated nonnegative `Long` within queue length before conversion to `Int` | Emits the selected song ID into the same car play flow. |
| Car shuffle / repeat / like | Custom action contains the current song ID; native membership and JS track validation | Existing context/application action, with stale-track events rejected. |

Expo Audio fallback interval/seek commands belong to its own player in stock Expo Go; they are not custom app queue-next/previous commands. Native method names and event units were checked against installed sources rather than inferred from button icon labels.

## Native listener ownership

| Registration | Owner | Removal and stale-event handling |
| --- | --- | --- |
| Android media-button/dismiss/skip broadcast receiver | Current Audio API installation | `MediaSessionManager.cleanup(owner)` unregisters; current bridge reference is cleared. |
| Android noisy-output receiver | Current Audio API installation | Same cleanup; registered once after initialization, previous installation cleaned before replacement. |
| Android focus listener/request | Current Audio API installation | Pause/reset/queue termination through the JS owner abandon focus; bridge cleanup also abandons. User intent versions prevent stale resume in JS. |
| Android volume receiver | Current Audio API installation, when explicitly observed | Idempotent enable/disable; bridge cleanup disables once. |
| Android notification MediaSession callback | Process-wide shared session; current bridge resolved per event | Notification hide clears metadata/commands. Session intentionally retained for browser token stability, rather than released on browser disconnection. |
| Car catalog/media-id/search/queue/custom-action listeners | `MavrixfyMediaLibraryModule` | `invalidate()` clears callbacks/actions/catalog. Current-track custom-action validation exists in both native and JS consumers. |
| iOS AVAudioSession route/interruption/reset/engine observers and optional volume/secondary-audio observation | `SystemNotificationManager` | Cleanup disables volume, removes observers, stops optional timer, disables interruption observation. |
| iOS Audio API remote-command selectors | Active `PlaybackNotification` | Each enable removes the same selector target first; hide disables/removes all controls and clears Now Playing. |
| iOS Audio API artwork request | Active `PlaybackNotification`, current artwork generation | Changed artwork/hide cancels request; completion requires the active generation. |
| Expo iOS remote-command blocks | `MediaController` command/token pairs | Removes returned opaque tokens before reactivation and at clear; does not remove other owners' targets. |

React Native 0.86.3 `RCTInstance.mm`, `RCTTurboModuleManager.mm`, and `RCTCxxBridge.mm` invalidation paths were also read when checking the main-queue notification cleanup: the host schedules teardown on its JS thread, and native modules invalidate on their own method queues. The Audio API cleanup checks `NSThread.isMainThread` before its synchronous dispatch to the main queue. Apple compilation and reload behavior still require a generated iOS build.

## Device verification still required

Use a rebuilt custom binary, test both a fresh installation and upgrade, and record actual observed results. All scenarios below are **NOT TESTED** here.

1. Start a two-song playlist, lock the screen for more than three minutes, and confirm continuous playback, metadata/artwork, one notification, and exactly one automatic advancement.
2. Repeatedly play/pause/next/previous/seek via notification and lock screen while foregrounded and backgrounded; confirm UI/engine/session alignment and seek never changes tracks.
3. Connect Android Auto, browse queue/liked/recent, choose/search a song, use queue/custom actions, then disconnect/reconnect the browser and recreate the activity without producing another token/player/notification.
4. While music plays, unplug wired headphones and disconnect an active A2DP device: playback should pause before speaker output and should not automatically restart on reconnection. Physical Bluetooth media buttons/routing remain a physical-device requirement.
5. Trigger permanent focus loss from another music app, a transient interruption/call, ducking/navigation speech, focus denial during a call, and an Android 15+ background-start attempt. Confirm pause/duck policy and that explicit user pause suppresses later automatic resume.
6. Switch quickly between tracks with slow/failing artwork and hide controls/reset the queue before a request finishes. Old art/metadata must not reappear. On iOS, repeat activation/clearing and confirm each remote command executes once.
7. Test iOS background/Control Center, incoming calls/Siri/alarms, route changes and media-services reset using a generated iOS build; compare the selected-stream timeline with the native displayed seek range.
8. Kill the app process and relaunch; distinguish the app's persisted paused restoration from unsupported OS/car cold-start media resumption. Manufacturer background/battery restrictions require representative physical devices.
