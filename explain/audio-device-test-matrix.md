# Mavrixfy audio device verification matrix

Prepared 2026-10-10, Asia/Calcutta. This is an execution checklist with honest pending results, not a claim of device certification. All real-device observations and statuses below are **NOT TESTED**.

The available Android SDK reported no connected device/emulator with `adb devices -l` and no configured AVD with `emulator -list-avds`. The host is Windows, has no Xcode, and has no generated native iOS project or connected Apple test device. These environment limitations prevent observations of actual audio output, lock-screen controls, Bluetooth, calls, manufacturer battery restrictions, and car behavior. Native compilation and JavaScript simulations cannot substitute for those observations.

## Capture procedure when a device becomes available

1. Use an authorized test device/account and rebuilt binary. Verify the exact package/build/runtime and record physical route/network/battery settings. Keep a short observation record for each scenario: timestamps, starting song/index/position, actions, audible outcome, UI/media-session outcome and any error.
2. On Android, capture only the needed app/session/audio diagnostics before and after the relevant operation. Select the real device serial explicitly. These are read-only example commands, not commands executed by this report:

```powershell
$audioAuditAdbPath = Join-Path $env:LOCALAPPDATA 'Android\Sdk\platform-tools\adb.exe'
$audioAuditSerial = '<device serial>'
$audioAuditPackage = 'com.mavrixfy.app'
& $audioAuditAdbPath devices -l
& $audioAuditAdbPath -s $audioAuditSerial shell getprop ro.build.version.sdk
& $audioAuditAdbPath -s $audioAuditSerial shell dumpsys package $audioAuditPackage
& $audioAuditAdbPath -s $audioAuditSerial shell pidof $audioAuditPackage
& $audioAuditAdbPath -s $audioAuditSerial shell dumpsys media_session
& $audioAuditAdbPath -s $audioAuditSerial shell dumpsys audio
& $audioAuditAdbPath -s $audioAuditSerial shell dumpsys activity services $audioAuditPackage
& $audioAuditAdbPath -s $audioAuditSerial shell dumpsys meminfo $audioAuditPackage
# Use the numeric package PID actually returned above, not PowerShell's reserved $PID.
$audioAuditAppProcessId = '<numeric package PID>'
& $audioAuditAdbPath -s $audioAuditSerial logcat -d --pid=$audioAuditAppProcessId
```

3. Compare media_session records for the Mavrixfy package: one intended session/token, advertised commands, playback state, active metadata/progress and terminal cleanup. Compare audio focus owners/routes before interruption/disconnect and after recovery. Record actual sound output independently; dumpsys alone cannot prove that a speaker/headset played or paused correctly.
4. For resource checks, sample the same PID repeatedly before/after a controlled mount/navigation sequence. The existing `scripts/android-performance.ps1` can collect labeled samples once a real device is available; its labels are user-provided and do not establish that a scenario ran. A PID change is process recreation, not ordinary navigation. Avoid treating one memory measurement or emulator thermal reading as proof of leak-free/device-efficient behavior.
5. For scenario 16, record whether the action was activity recreation, an OS process kill, a deliberate force-stop, removal from Recents, or a reboot. These have different lifecycle expectations. Do not accidentally erase data while performing the upgrade/persistence case. A force-stop observation does not prove recoverability from every OS kill policy.
6. For iOS, use Xcode/device logs plus simultaneous app/Control Center/route observations on the installed generated build. Record the build, OS, physical route, actual interruption and which controls were available. Do not substitute an Android result or a stock Expo Go observation for the patched custom iOS binary.
7. Keep captures local until reviewed. Redact account/user identifiers, signed media URLs and query tokens, authentication/cookies, device/network addresses and unrelated app metadata before sharing. Do not export keystores/signing material, environment files, app private storage, Firebase credentials, full account databases or unfiltered broad device dumps. Include only the minimal sanitized diagnostic excerpts supporting the observation.
8. Update the relevant observed-result/status cells with a concrete result and evidence reference. Use PASS, FAIL, NOT TESTED or NOT APPLICABLE with a recorded reason/build/runtime; unavailable required tests remain NOT TESTED. A rerun after a fix gets a new evidence entry rather than overwriting the original failure without trace.

## Device release gate

Audio native changes are not device verified until the required 18 rows and applicable extended checks have actual observations on the supported rebuilt Android targets and generated iOS target. Before shipping a platform/runtime, resolve failures in its supported cases and explicitly document unsupported capabilities or blocked environments; pending rows are not passes. The core gate includes continuous screen-off playback, single notification/session, correct independent OS controls, one completion transition, focus/noisy-route safety, latest-intent/queue consistency, bounded error recovery, account isolation, managed-download validation, cleanup and expected paused relaunch. Car certification requires the applicable car/head-unit environment and running-bridge limitation to be exercised.

Keep successful JavaScript/static/native-build evidence, device evidence and outstanding whole-project lint/dependency limitations separate. The current **NOT TESTED** matrix remains a release verification requirement; it does not invalidate the deterministic fixes already covered by automated tests, and it does not authorize a claim that operating-system playback behavior is production certified.
